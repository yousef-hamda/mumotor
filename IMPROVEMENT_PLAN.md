## Audit Summary

**What works well:**
- Clean multi-tenant data isolation: every domain table has `websiteId` FK + `onDelete: Cascade` + ownership middleware
- 12 polished, distinct React templates with a real WebGL shader layer and animated concept cards
- A solid builder wizard (8 steps, live preview, localStorage persistence)
- Transactional booking with concurrency guard (`P2002` → 409 conflict)
- 180+ passing tests (26 unit / 70 integration / 84 E2E, 0 console errors)
- Timing-safe enrollment code comparison, rate limiting on auth endpoints
- Stripe Checkout wired (real + demo mode)
- Redis caching for published site HTML
- Nodemailer + 7 transactional email types
- 3 cron jobs (reminder / daily open / schedule report)

**What is critically broken or missing:**
- Billing is entirely unenforced — paying users get zero additional access
- JWT secret has a public fallback string that would sign all production tokens if not set
- Uploaded photos go to an ephemeral local filesystem — wiped on every Railway deploy
- No password reset flow exists at all
- No email verification despite the field existing in the schema
- Students cannot submit reviews; every published site shows empty testimonials
- The published site URL shown to teachers (`slug.mumotor.com`) does not exist technically
- Zero analytics instrumentation — no way to measure anything
- Template copy is hardcoded English despite the product targeting Hebrew/Arabic Israel

## Tier 0 — Security Blockers

These are exploitable right now and must be fixed before any production user touches the product.

---

### T0-1. JWT Secret Has a Public Default

**File:** `packages/backend/src/config/env.ts`

`JWT_SECRET` defaults to `"dev-secret-change-me-in-production"`. If this environment variable is omitted from Railway (easy to forget during a first deploy), every JWT in production is signed with a well-known public string. Any attacker who knows this can forge tokens for any `userId` and impersonate any teacher or admin.

**Fix:**
- Make `JWT_SECRET` required in the Zod env schema with `.min(32)` validation and no default value.
- Zod will exit the process at startup if the variable is absent.
- Add to Railway deployment checklist.

---

### T0-2. CORS Is Permissive in Production

**File:** `packages/backend/src/app.ts`

`origin: '*'` is set with an inline comment: `// tighten in prod`. It was never tightened. Auth tokens are sent as `Authorization: Bearer` headers AND as cookies in parts of the student flow. With `*` origin, any website can make credentialed cross-origin requests to the Mumotor API on behalf of any logged-in user.

**Fix:**
- Change `origin: '*'` to `origin: process.env.FRONTEND_URL`.
- Reject preflight requests from unlisted origins.

---

### T0-3. Stripe Webhook Secret Is Optional

**File:** `packages/backend/src/config/env.ts` + `src/services/billing/stripeWebhook.ts`

`STRIPE_WEBHOOK_SECRET` is optional in the Zod schema. The webhook handler at `POST /stripe/webhook` uses this secret to verify the `stripe-signature` header. If the variable is absent, the verification call receives an empty string and may silently pass (depending on the Stripe SDK version). Anyone who discovers the webhook URL can POST a crafted `checkout.session.completed` payload to upgrade any user to STUDIO for free.

**Fix:**
- When `STRIPE_SECRET_KEY` is set, make `STRIPE_WEBHOOK_SECRET` required.
- Return `400` immediately if the signature is missing or invalid.

---

### T0-4. Upload Rate Limiting Absent

**File:** `packages/backend/src/routes/websites.ts` (media upload section)

`POST /websites/:id/media` has no rate limit applied. An authenticated user can upload files at unlimited frequency. Media is stored as base64-decoded files on local disk. This is a denial-of-service vector against both disk space and the Node.js event loop (base64 decode is synchronous for large payloads).

**Fix:**
- Apply the existing `rateLimit` middleware: max 20 uploads per user per hour.
- Add a max `Content-Length` guard of 10 MB.

## Tier 1 — Product Blockers

These do not create security holes but the product cannot be used commercially without fixing them.

---

### T1-1. No Plan Enforcement — Billing Is Decorative

**Files:** `packages/backend/src/routes/websites.ts`, `src/routes/subscriptions.ts`

Three plans exist with distinct feature lists (FREE: 1 site / 20 students; PRO: 3 sites / 200 students / custom domain; STUDIO: 10 sites / white-label / API). Stripe checkout works. But there is **zero backend enforcement** of any limit anywhere. A FREE user can:
- Create unlimited websites (`POST /websites`)
- Enroll unlimited students
- Use every premium template
- Access every API endpoint

The feature lists on the billing page are display-only strings. No middleware, no service-layer check, and no database query reads `subscription.plan` before any write operation.

**Fix:**
- Add a `checkPlanLimit(userId, feature)` middleware that loads the user's subscription.
- Gate `POST /websites` on website count vs. plan cap.
- Gate enrollment on student count vs. plan cap.
- Gate premium templates (glass suite, prestige, obsidian, prism) on PRO+.
- Build a `features` map driven by plan tier.

---

### T1-2. Uploaded Photos Are Lost on Every Deploy

**Files:** `packages/backend/src/routes/websites.ts` (media upload), `packages/backend/prisma/schema.prisma` (`Media.cdnUrl`)

Uploaded teacher photos (instructor photo, car photo, gallery) are saved to `packages/backend/uploads/` — a local filesystem directory. Railway containers use an **ephemeral filesystem** that is wiped on every deploy, restart, or crash. The `railway.toml` file does not configure a persistent volume. The `Media.cdnUrl` field in the Prisma schema is always `null` — CDN integration was planned but never implemented.

**Result:** Teachers upload their instructor photo during the wizard. After the first production deploy, their published sites show broken image links.

**Fix (immediate):** Configure a Railway persistent volume at the `/uploads` path.
**Fix (proper):** Implement S3 or Cloudflare R2 upload. The `Media` model already has `cdnUrl` — write the CDN URL there. Use `sharp` (already a dependency) for resizing before upload. The upload endpoint already has the placeholder comment.

---

### T1-3. No Password Reset Flow

**Files:** `packages/backend/src/routes/auth.ts`

There are three auth routes: `register`, `login`, `me`, `change-password`. There is no `forgot-password` route, no reset-token mechanism, no recovery email, and no expiring-token schema or table.

**Result:** Any user who forgets their password is permanently locked out. They must contact the founder directly. This is a demo prototype constraint, not a product constraint.

**Fix:**
- `POST /auth/forgot-password` — generate a short-lived signed token (nanoid, 1h TTL), store in Redis `reset:${token}` → email it.
- `POST /auth/reset-password` — verify token via GETDEL, update `passwordHash`, invalidate all sessions.
- Use the existing `emailService` for the reset email.

---

### T1-4. No Email Verification

**Files:** `packages/backend/prisma/schema.prisma` (`User.emailVerified`), `packages/backend/src/routes/auth.ts`

`User.emailVerified` is defined as `Boolean @default(false)`. No code path ever sets it to `true`. Registration succeeds instantly for any email address — including typos, fake addresses, or addresses owned by other people.

**Consequences:**
- Transactional emails (booking confirmations, daily reports) may bounce silently.
- Someone can register with a teacher's real email and access that teacher's name in the system.
- Teachers may never receive critical notifications if they mistype their email.

**Fix:**
- On `POST /auth/register`: generate a signed verification token, store in Redis, send a verification email.
- Gate the `/dashboard` route (client and server) behind `emailVerified = true`.
- Add `GET /auth/verify-email?token=` to set the flag.
- Allow resending via `POST /auth/resend-verification`.

---

### T1-5. Students Cannot Submit Reviews

**Files:** `packages/backend/src/routes/reviews.ts`

The `Review` model exists. Admin moderation exists (`PATCH /reviews/:id` for APPROVE/REJECT/REPLY). But there is no `POST /reviews` public endpoint. Students have no mechanism to submit reviews through the product.

**Result:** Every published teacher site shows an empty testimonials section unless reviews are seeded manually in the database. This defeats one of the most prominently advertised features ("Reviews" is listed on the landing page dark section as a core feature).

**Fix:**
- `POST /driving-school/:websiteId/reviews` — public endpoint (no auth required, rate-limited 1/hour/IP).
- Accepts: `authorName`, `authorEmail`, `rating (1–5)`, `text`. Optional: `enrollmentId` (links to a real student).
- Creates `Review` with `status: PENDING`.
- Sends a "New review pending approval" notification to the teacher.
- Teacher approves from the Reviews dashboard tab.

---

### T1-6. The Published URL Shown to Teachers Does Not Exist

**Files:** `packages/frontend/src/pages/builder/BuilderWizard.tsx` (done step)

The wizard's final screen shows: **"Your site is live at david-cohen.mumotor.com"**. There is no wildcard DNS entry, no nginx subdomain routing, no Cloudflare proxy rule for `*.mumotor.com`. The actual working URL is `mumotor.com/p/david-cohen`. If a teacher copies the shown URL and pastes it to a student, it returns a DNS resolution failure.

**Fix (immediate, 30 minutes):** Change the done-screen URL display to show the real path format `mumotor.com/p/{slug}`.

**Fix (long-term):** Implement real wildcard subdomain routing:
1. Cloudflare DNS: `CNAME * → mumotor.com`
2. Railway / nginx: `server_name ~^(?<slug>.+)\.mumotor\.com$` → proxy to the React SPA, which reads `slug` from the hostname and renders `/p/$slug`.
This makes the product promise real.

## Tier 2 — High Priority

---

### T2-1. Zero Analytics Instrumentation

**Files:** No analytics files exist anywhere in the codebase.

There is no page view tracking, no event tracking, no third-party analytics script, no funnel data, and no time-series metrics. The admin panel shows raw DB totals (users/websites/published/enrollments) but with no date filter, no growth chart, and no cohort view.

**Result:** You cannot answer any investor question about the product:
- What is the wizard completion rate?
- Which template do teachers pick most?
- How many published sites have active bookings?
- What is month-over-month growth?
- Where do users drop off in the funnel?

**Fix:**
- Add Plausible Analytics (self-hosted, privacy-safe, GDPR-compliant, good for Israeli market) or PostHog.
- Instrument 8 key events: `wizard_start`, `wizard_step_{n}`, `template_selected`, `publish`, `customize_open`, `customize_save`, `student_enrolled`, `lesson_booked`.
- Add server-side daily snapshot: websites published, lessons booked, active students — written to a `DailyMetric` table by cron.
- Extend admin panel with 30-day sparklines for each metric.

---

### T2-2. Dual Rendering Pipeline — Architectural Confusion

**Files:** `packages/backend/src/routes/ai.ts`, `packages/backend/src/services/ai/`, `packages/frontend/src/pages/editor/EditorPage.tsx`, `packages/frontend/src/pages/public/PublicSite.tsx`

Two completely separate site-building systems coexist with no clear path between them:

**Pipeline A (Legacy):** `EditorPage` in the dashboard → `POST /ai/v2/generate-website` → deterministic HTML string (9 presets, no Customize Mode) → stored in `Website.publishedHtml` → served at `GET /site/:slug`.

**Pipeline B (Current):** BuilderWizard → 12 React templates → Customize Mode → stored in `website.configuration.customization` → rendered at `/p/:slug`.

The `EditorPage` that teachers see in their dashboard after publish uses Pipeline A. Their Customize Mode edits (done via Pipeline B) do not appear in the editor. The two pipelines diverge on every save.

**Fix:**
- Deprecate Pipeline A. Remove `EditorPage` and replace the dashboard "Edit" button with a link to `/customize/:id`.
- Remove the `POST /ai/v2/generate-website` endpoint from the product surface.
- The `GET /site/:slug` route can remain as an SEO-optimized path by server-rendering the React templates (Vite SSR), but the editor surface must be unified.
- Keep the 9-preset backend service only if needed for backward compatibility with old published sites.

---

### T2-3. Template Copy Is Hardcoded English

**Files:** All 12 template `index.tsx` files under `packages/frontend/src/templates/`

i18next is installed and configured with translation files for HE/AR/EN. The wizard has a language selector. `Website.locale` is stored in the database. But all 12 React template components have hardcoded English text baked into JSX: `"Book a Lesson"`, `"About the Instructor"`, `"Our Packages"`, `"Areas We Cover"`, etc.

The `data.locale` field flows through `TemplateData` but is never used to select alternative copy strings. `publicToTemplateData()` does not inject locale-appropriate defaults.

**Result:** A Hebrew-speaking teacher in Haifa builds their site, selects Hebrew (`HE`), publishes — and their public site shows fully English text. The entire Israel/Hebrew market promise is broken.

**Fix:**
- Create a `templateCopy.ts` with locale-keyed default strings for every section heading.
- `publicToTemplateData()` injects locale-appropriate defaults into `data.copy.*`.
- Templates use `data.copy.key ?? defaultCopy[locale].key` — falling back to English only if locale copy is missing.
- Since `data.copy` overrides already work in Customize Mode, this requires no template restructuring — just populating the defaults.

---

### T2-4. Wizard Progress Is Lost on Browser Close

**Files:** `packages/frontend/src/lib/wizard.ts`, `packages/frontend/src/pages/builder/BuilderWizard.tsx`

The 8-step wizard saves all progress to `localStorage` only. No server-side draft exists. If a teacher spends 40 minutes filling in business details, working hours, lesson plans, social links, and selecting a template — then closes the browser, switches devices, or has a browser crash — everything is lost.

**Fix:**
- At the end of Step 1 (business info), if the user enters their email, silently `POST /wizard/drafts` to save partial progress server-side.
- Generate a draft token, store in a `WizardDraft` table (or a signed cookie).
- Email the teacher a "Resume your site setup" link if they don't complete within 24h.
- This doubles as lead capture for incomplete signups.

---

### T2-5. Currency Mismatch Across the Product

**Files:** `packages/frontend/src/pages/dashboard/Billing.tsx`, template components (e.g., package price rendering)

The billing page shows prices in USD: `$29/mo`, `$79/mo`. Template sections and the driving school UI show prices in `₪` (NIS — Israeli shekel). The product is built for Israel. The inconsistency creates distrust and complicates the pricing decision.

**Fix:**
- Decide on one billing currency. Recommendation: **NIS (₪)** — the target market is Israeli, and local pricing (₪79/mo for PRO, ₪199/mo for STUDIO) converts better mentally than USD for an Israeli teacher.
- Sync the billing page, all plan card labels, and the "price per lesson" field in SiteSettings to use the same currency symbol and formatting.
- Consider annual billing at a 2-month discount: ₪790/yr (vs. ₪79 × 12 = ₪948).

---

### T2-6. No SEO on Published Teacher Sites

**Files:** `packages/frontend/src/pages/public/PublicSite.tsx`, `packages/backend/prisma/schema.prisma` (`Website.seoSettings`)

`Website.seoSettings` is defined in the Prisma schema as a JSON field. It is **never written by any route and never read by any service or template**. Published React sites at `/p/:slug` render with no meaningful `<title>`, no `<meta name="description">`, no Open Graph tags, and no structured data.

Google crawls `/p/david-cohen` and finds a client-side React SPA rendering behind JavaScript with generic or missing meta tags. It will rank near zero for `"[city] driving instructor"` searches.

**Fix:**
- Implement server-side head rendering. Options:
  - Vite SSR for the `/p/:slug` route (proper solution, requires build change)
  - React Helmet Async (immediate, imperfect for crawlers without prerender)
  - A thin prerender service (Rendertron/Puppeteer) for the `/p/*` path
- Populate from `publicToTemplateData`: `<title>{instructorName} — Driving Lessons in {city}</title>`
- Add `<meta name="description">` from instructor bio or tagline
- Add `<link rel="canonical" href="https://mumotor.com/p/{slug}">`
- Add `<script type="application/ld+json">` with `LocalBusiness` schema: address, phone, priceRange, aggregateRating
- Write `seoSettings` on publish from the wizard's business info fields
- Add a "SEO" section to the dashboard settings page

## Tier 3 — Product Features

These are genuine product gaps that reduce the value proposition for teachers and students.

---

### T3-1. No Lesson Cancellation

**Files:** `packages/backend/src/routes/drivingSchool.ts`

Teachers can view bookings in the daily report but cannot cancel a booking from the dashboard. There is no `PATCH /bookings/:id/status` or `DELETE /bookings/:id` endpoint. Students also have no cancellation path.

**Impact:** Teachers manage cancellations by phone/WhatsApp, defeating the booking management system. Students who need to cancel have no self-service option.

**Fix:**
- `PATCH /driving-school/:websiteId/bookings/:id/cancel` (teacher-owned) — sets status to `CANCELLED`, sends cancellation email to student.
- Student self-cancellation via magic link: can cancel up to `N` hours before lesson (configurable in SiteSettings).
- Dashboard schedule view shows cancelled bookings in a distinct style.

---

### T3-2. No Student Portal

**Files:** `packages/frontend/src/pages/public/` (student-facing pages)

Students can enroll, book a lesson, and receive emails. After booking, they have no self-service interface to:
- See upcoming/past lessons
- Cancel a booking
- Download a receipt
- Contact their instructor through the platform

The magic link flow is one-shot and stateless. After following it once, the student has no persistent access.

**Fix:**
- A minimal student portal at `/p/:slug/my-lessons` — accessed via magic link (no password needed).
- Shows: upcoming bookings (date/time/status), past lessons (count), instructor contact info.
- "Cancel lesson" button (within the allowed window).
- "Request a new lesson" CTA links to the booking flow.

---

### T3-3. No Waiting List

**Files:** `packages/backend/src/routes/drivingSchool.ts` (availability endpoint)

When all slots for a given day are booked, the booking UI shows no available times and the student has no recourse. Driving instructors in Israel are frequently fully booked weeks in advance. A waiting list is a standard feature for this market.

**Fix:**
- `POST /driving-school/:websiteId/waitlist` — stores `{email, websiteId, preferredDates[]}`.
- New `Waitlist` Prisma model.
- When a booking is cancelled (T3-1 fix), a cron job notifies the first matching waitlist entry.
- Teacher sees the waitlist count in the dashboard.

---

### T3-4. No Referral / Word-of-Mouth Flow

**Files:** Not implemented.

Happy students are the primary growth channel for a local driving instructor. There is no mechanism for a student to refer a friend. In Israel, word-of-mouth (WhatsApp sharing) drives most local service discovery.

**Fix:**
- Generate a unique referral link per enrollment: `mumotor.com/p/{slug}?ref={enrollmentId}`.
- When a referred student enrolls and completes their first lesson, flag the referral in the system.
- Teacher can see referral counts in the dashboard and offer the referrer a lesson credit manually.
- Lightweight to implement (the `ClientEnrollment` model can gain a `referredBy` FK), high word-of-mouth value.

---

### T3-5. Verified Reviews — Integrity Gap

**Files:** Once T1-5 is fixed, this applies to the new review endpoint.

Even with public review submission added, anyone can claim to be a student. An instructor could fill their site with fake 5-star reviews.

**Fix:**
- Reviews submitted via an authenticated magic link session carry the student's `enrollmentId` automatically. Mark these as `verified: true`.
- Reviews submitted anonymously (no magic link) are marked `verified: false` and display without a "Verified student" badge.
- Teachers see the verification status in the reviews dashboard.
- Investors and students can trust verified reviews; unverified reviews are still visible but clearly labeled.

---

### T3-6. Post-Publish Onboarding Checklist

**Files:** `packages/frontend/src/pages/dashboard/Dashboard.tsx`

After a teacher publishes their site, they land on the dashboard with no guidance on what to do next. They may not know to share their enrollment link, set up their booking hours, add their instructor photo, or how to give their daily code to students.

**Fix:**
- A dismissible onboarding checklist widget in the dashboard home:
  - [ ] Share your enrollment link with students
  - [ ] Verify your lesson schedule and working hours
  - [ ] Add your instructor photo
  - [ ] Create today's daily access code
  - [ ] Request your first review from a past student
- Each step links directly to the relevant dashboard section.
- Persist completion state in `localStorage` (or a `UserPreferences` table).

---

### T3-7. No Lead Capture at Wizard Start

**Files:** `packages/frontend/src/pages/builder/BuilderWizard.tsx` (Step 1 — Business Info)

The wizard does not capture the teacher's email until Step 7 (account creation). A teacher who starts the wizard, reaches Step 4, and closes the browser is lost forever — no email, no follow-up possible.

**Fix:**
- At the end of Step 1 (after entering business name and description), show: **"Save your progress — enter your email so we can resume where you left off."** (optional, skippable).
- Store the email + partial wizard state in a `WizardDraft` table.
- 24h later: automated email "Your Mumotor site is 40% ready — finish it in 5 minutes."
- 72h later: "3 driving instructors in your area published this week — here's what their sites look like."

## Tier 4 — Growth & Business

---

### T4-1. The "AI" Branding Is Misleading

**Files:** `packages/backend/src/routes/ai.ts`, `packages/backend/src/services/ai/`

The product routes are `/ai/v2/`, the service directory is `services/ai/`, the CLAUDE.md says "AI/no-code website builder" — but there are **zero AI API calls anywhere in the codebase**. `generator.ts` contains an explicit comment: `"Hook point for an optional AI Stage 1 bio-enhancement call when an AI provider key is configured — NOT IMPLEMENTED"`. Generation is purely deterministic template rendering with hardcoded palettes and layouts.

**Options:**
1. **Remove the AI branding** (honest): call it "smart template generation." Reduces marketing claim but avoids credibility risk.
2. **Actually add AI** where it creates real value:
   - **Bio generator**: teacher enters name + years + areas → Claude Haiku writes a compelling 3-sentence instructor bio (used in the About section).
   - **SEO description**: generate the `<meta name="description">` from the teacher's profile.
   - **Package naming**: suggest lesson package names in the teacher's locale (HE/AR/EN).
   - **Review response drafts**: when a teacher clicks "Reply to review," offer a one-click AI-drafted response.
   - Using Claude Haiku, each of these costs ~$0.001 per call — negligible at SaaS scale.

---

### T4-2. PRO Plan Features Don't Justify the Price

**Files:** `packages/frontend/src/pages/dashboard/Billing.tsx`

Current PRO plan features: 3 websites, all templates, 200 students, custom domain. Two of these (all templates, custom domain) do not work as advertised (plan not enforced; custom domain not implemented). The price cannot be justified until the plan is real.

**Recommended PRO features (₪79/mo):**
- Unlimited students (vs. 20 on FREE)
- Student portal (magic link → booking history + cancellation)
- WhatsApp Business integration (send booking confirmation via WA Cloud API)
- Lesson cancellation self-service for students
- Review request emails (auto-sent 24h after lesson completion)
- Analytics dashboard (lesson count by week, busiest booking days)
- Remove "Powered by Mumotor" footer attribution

**Recommended STUDIO features (₪199/mo):**
- Multi-instructor support (one school account, multiple teacher profiles)
- White-label / custom domain (requires T1-6 infrastructure)
- API access for Google Calendar sync and accounting integrations
- Bulk SMS (Twilio) in addition to bulk email
- Priority support with 4-hour response SLA
- Advanced analytics: student retention rate, revenue tracking, funnel analysis

---

### T4-3. Israeli Payment Methods Are Not Covered

**Files:** `packages/backend/src/services/billing/stripeWebhook.ts`

Stripe Checkout is implemented. Stripe supports Israel but with higher decline rates for Israeli cards when using a non-Israeli merchant account. Israeli teachers primarily pay with:
- **Bit** — the dominant Israeli mobile payment app
- **PayBox** — peer-to-peer / business payments
- **Pepper Pay** — Israeli fintech
- **Cal / Leumi Card / Isracard** — Israeli credit card networks that may not process well through a US Stripe entity

**Fix:**
- Register a Stripe account under an Israeli entity for better local card acceptance.
- Consider adding **Cardcom** or **Tranzilla** as alternative payment gateways (both support Israeli credit cards + Bit directly).
- For monthly recurring subscriptions, consider offering an **annual plan** at 2 months free (₪790/yr) — easier to pay via a single credit card charge than a recurring international subscription.

---

### T4-4. No Formal Monorepo Workspace Configuration

**Files:** Root (no `package.json` with workspaces)

There is no root `package.json` with `"workspaces": ["packages/*"]`. The two packages are installed separately and not formally linked. TypeScript types (`TemplateData`, `WizardConfig`, `PublicSettingsResponse`) are duplicated between backend and frontend by convention and become out of sync.

**Fix:**
- Add root `package.json` with npm workspaces.
- Create `packages/shared` with shared TypeScript types and Zod schemas.
- Both backend and frontend import from `@mumotor/shared`.
- This eliminates type drift between the wizard config the backend stores and the frontend reads.

## Tier 5 — Technical Debt

---

### T5-1. Base64 File Uploads Block the Event Loop

**Files:** `packages/backend/src/routes/websites.ts` (media upload)

Media uploads accept base64-encoded image data in the JSON body. A 4MB photo becomes ~5.3MB of JSON, which:
- Buffers entirely in memory before processing
- Decodes synchronously, blocking the Node.js event loop
- Uses 33% more bandwidth than binary multipart upload

`multer` is already installed as a dependency but is not used for the media upload endpoint.

**Fix:**
- Replace base64 JSON upload with `multer` multipart form upload.
- `multer` streams files directly to disk (or straight to S3 with `multer-s3`).
- Remove the base64 decode path entirely.

---

### T5-2. Cron Jobs Have No Failure Visibility

**Files:** `packages/backend/src/services/jobs/jobService.ts`

Three cron jobs run in-process inside the Express server. If a job throws, the error is swallowed silently. If the server restarts mid-job, the job is abandoned (e.g., a teacher's daily report email is not sent). There is no monitoring, no retry, no dead-letter queue, and no job health endpoint.

**Fix:**
- Wrap each job in a try/catch that logs the error and writes a failed `Notification` row to the DB so the admin panel can surface it.
- For the booking reminder job specifically, use BullMQ (Redis-backed) — already have Redis available — to guarantee at-least-once delivery and prevent duplicate emails on retries.
- Add a `GET /admin/cron-health` endpoint that shows last-run timestamp and status for each job.

---

### T5-3. No Test Coverage for Billing, Admin, or Reviews

**Files:** `packages/backend/test/integration.mjs`

The integration test suite (70 tests) covers auth, websites, driving school settings, booking, student management, and magic links. It has zero coverage for:
- `/subscriptions` (checkout + plan enforcement once added)
- `/admin` endpoints
- `POST /reviews` (once added)
- Media upload
- Rate limiting behavior
- i18n / locale-based content

**Fix:**
- Add a `billing.integration.mjs` suite: checkout creates subscription, plan limits are enforced.
- Add `admin.integration.mjs`: stats returns expected counts, user list is gated by role.
- Add review submission + moderation to the existing driving school suite.

### T5-4. `Page` and `Section` Models Are Dead Code

**Files:** `packages/backend/prisma/schema.prisma`

Both `Page` and `Section` Prisma models are fully defined with foreign keys, indexes, and cascade rules — but have zero API routes, zero service code, and zero frontend references. They are orphaned schema from a planned block-based page editor that was never implemented.

**Fix:**
- Either implement the page/section editor as a planned feature, or delete these models and generate a migration to drop the tables.
- Keeping dead schema models creates confusion for new contributors and adds noise to the database.
